# 发布流程（RELEASING）

本文件说明本工具包的**版本号策略**、**变更记录规范**、**发布前检查单**与**发布步骤**。

---

## 1. 版本号策略（SemVer）

`MAJOR.MINOR.PATCH`，语义按**使用者能观察到的变化**判定，不按内部重构：

| 变更 | 版本位 | 例子 |
|---|---|---|
| 破坏性：CLI 参数改名/删除、退出码含义变化、环境变量改名、默认值改变导致判定结果不同、对象布局或会话格式的假设变化 | **MAJOR** | 把某个默认取回源去掉、缓存文件名再改、退出码 3 的含义变 |
| 新增：新参数、新环境变量、新取回源类型、新报告字段、新增支持的平台 | **MINOR** | 新增 `--local-source` 注入、新增一种中转目录布局 |
| 修复：bug 修复、文案修正、性能优化、内部重构（行为不变） | **PATCH** | 修缓存键的边界、修冲突判定的消息 |

补充规则：

- 处于 **0.x** 阶段时允许 MINOR 位承载破坏性变更，但**必须在 CHANGELOG 显式标注 `Breaking`**。
- **判定口径的任何改动 = 至少 MINOR**：这套工具的价值在判据，判据变了使用者必须知道。
- 退出码是**对外契约**：动它一律 MAJOR（使用者会拿它做 `if exit == 3` 这种分支）。
- 一个版本一个主题；混装多个主题就拆成多次发布。
- 版本号只增不减；发错了就发下一个补丁版本回退，**不重打已发布的 tag**。

---

## 2. 变更记录规范（CHANGELOG）

`CHANGELOG.md`，倒序（最新在最上），每次发布一节：

```markdown
## [0.2.0] - 2026-10-01

### Added
- 新参数 / 新取回源 / 新平台支持。

### Changed
- 默认值或行为变化（写清「旧 → 新」与恢复方式）。

### Fixed
- 修掉的具体问题（写清现象与影响面）。

### Breaking
- 使用者要做什么才能继续用（迁移动作），没有就写「无」。
```

约定：

- 面向**使用者**写（他能观察到什么），不写内部流水账；
- 每条尽量带「影响面」与「迁移动作」；
- 未发布期间的改动先写进 `## [Unreleased]`，发布时改成版本号 + 日期。

## 3. 发布前检查单

按顺序跑，任一项不过就不发：

- [ ] `node scripts/verify-source.mjs .` → `ALL CHECKS PASSED`
      ⚠️ 要在**你自己的机器**上覆盖实名规则（机器名 / 用户名 / 本机目录名 / 同步产品名 / 内部专有名 /
      私人称呼）时，先注入 `BUILD_MACHINE_NAMES` / `BUILD_USER_NAMES` / `BUILD_LAYOUT_ROOTS` /
      `BUILD_SYNC_PRODUCTS` / `BUILD_INTERNAL_TERMS` / `BUILD_PERSONAL_TERMS` 再跑；
      不注入时只跑通用形态规则（脚本会打印 `注入 0 条` 的提示，属**预期**而非失败）
- [ ] **阳性对照**（强烈建议每次发布都做一遍）：随手注入一个**你确信存在**的词（例如某个模块名），
      确认扫描器**真的报红** —— 只有"能报红"的扫描器，它报的 0 命中才可信
- [ ] `node scripts/test-fixtures.mjs` → `断言 全过`（`SKIP` 必须为 0）
- [ ] **真实环境冒烟**：对你自己的 home 跑一次只读对账
      （先 `node attachments-audit.mjs --print-config` 看清路径来源，再 `node attachments-audit.mjs`），
      确认判定与退出码符合预期。**只读**，不会改任何东西
- [ ] **隐私扫描**：仓库里没有本机路径、机器名、用户名、个人称呼、内部文档名、内部编号
- [ ] `CHANGELOG.md` 已写、日期已填、`Breaking` 已标注（若有）
- [ ] `package.json` 的 `version` 已按 §1 规则递增
- [ ] **许可检查（若本次动了许可）**：许可变更必须**三处齐改** ——
      ① 仓根 `LICENSE`（官方全文，不改写条款文字）② `README.md` 的「许可与发布状态」段
      ③ `package.json` 的 `license` 字段（SPDX 标识）。
      ⚠️ 许可变更**只约束未来版本**：已按旧许可发布的版本，他人已获得的授权收不回 —— 这句必须写进 README
- [ ] `npm pack --dry-run` 内容正确（若决定发 npm；只发 Release 则跳过）

## 4. 发布步骤

```bash
# 1) 版本与记录：改 package.json 的 version、把 CHANGELOG 的 Unreleased 改成版本号 + 日期
# 2) 全套验证
node scripts/verify-source.mjs .
node scripts/test-fixtures.mjs
# 3) 真实环境冒烟（见 §3 第 4 条）
# 4) 提交与标签
git add -A
git commit -m "release: v0.1.0"
git tag -a v0.1.0 -m "v0.1.0"
git push <remote> main --tags
# 5) 发布说明：直接贴 CHANGELOG 里本节的正文
```

**仓名、是否与他人合仓、是否发 npm、许可是什么** —— 这四项都属于**维护者拍板项**；
在拍板之前：**不建远端仓、不推送、不打 tag、不发 npm**。

若日后决定发 npm：

```bash
npm publish --access public   # 先确认包名可用；LICENSE/README 必须已在 files 里
```

> 发 npm 的前提是包名未被占用，且愿意承担长期可用性承诺。
> 只发 Release（使用者拿到目录直接 `node xxx.mjs`）是更轻的选择 —— 本工具包零依赖、无构建步骤，
> **不需要安装步骤**，这也是它适合只发 Release 的原因。

## 5. 双端发布（镜像）的已知坑

若同时发布到两个代码托管平台（主 + 镜像），下面几条是实测踩过的：

1. **有的平台建仓后默认是私有**：即使建仓请求里写了「公开」，实测建出来的仍是私有
   （表现为「公开仓」只有自己能看，匿名 API 一律 404）。建仓后需再显式改一次可见性，
   且**必须带上仓名字段**（否则报 `name is missing`）。
2. **复核要看「匿名视角」**：用带 token 的 API 读得到 ≠ 公开。
   权威判据 = 匿名请求仓库信息能看到，且匿名能取到文件内容。
3. **重打过的 tag 推送会被拒**（提示像认证失败，其实是 non-fast-forward）→ **只对 tag 用 `--force`**，
   分支仍走非快进保护。
4. **有的平台不会因 push 自动建仓**：目标仓不存在时 push 直接 404；建仓只能走 API 或网页。

（以上为通用经验，不针对任何具体平台；实际发布前以各平台当前文档为准。）

## 6. 与「文档侧」的互链

若这批还发布方法论文档（例如「换机后含图会话报错的根因怎么查」这类文章）：

- 工具包 README 给出文档链接；
- 文档侧给出本仓库链接与**引用时的版本号**（引用的是 vX.Y.Z 时的行为）；
- 两边版本号各自独立，互相引用时写明版本，避免一边改了另一边不知情；
- 占位符约定：`<repo-url>`（本仓地址）、`<docs-repo-url>`（文档仓地址）—— 替换时三处一起改：
  本文件、README 的「许可与发布状态」段、以及脚本头部注释里指向的说明（若有）。
